01 — Stack

Intentionally simple.

No build toolchain, no bundler, no framework, no npm. The constraint was a feature: a static site that can be deployed anywhere and understood by any developer in under 10 minutes.

LayerChoiceWhy
HTML/CSS Vanilla, hand-authored Full control, no abstraction tax, works everywhere
JavaScript React 18 UMD + Babel Standalone JSX authoring without a build step for case studies; loaded from CDN with SRI hashes
Fonts Geist, JetBrains Mono, Playfair Display, Space Mono via Google Fonts Editorial hierarchy: one grotesque (all weights), one true mono, one serif for counterpoint
Color OKLCH throughout Perceptually uniform — changing lightness doesn't shift perceived hue
Analytics Google Analytics 4 (G-0SSHKT8LPF) Case study click tracking, Q&A engagement events, session data
Hosting GitHub Pages (fable-updates branch) Free, fast, zero ops, direct git deploy

The style-switcher (five color themes: Studio, Cream, Plasma, Acid, Cobalt, Ember) persists the selected theme in localStorage and applies it via a data-theme attribute on <html>. All colors are defined as OKLCH custom properties, so every theme variant is a single :root block swap.

02 — Build pipeline

One Node script, no dependencies.

Case studies live in a single case-studies.jsx file as a CASE_STUDIES object — one source of truth for content, schema, and rendering. A build.js script (Node, no npm installs) does two things:

Bundles CSS: concatenates five stylesheets (styles.css, style-switcher.css, styles-hero.css, styles-rest.css, case-study.css) into dist-css/case-study-bundle.css. Reduces CSS requests from 6 to 2 (bundle + Google Fonts) on every case study page.

Generates static shells: writes work/<slug>/index.html for each of the 8 case studies, with the correct <title>, meta description, OG tags, and Twitter card baked into the static HTML. Social crawlers get real metadata without running JavaScript. Each shell loads the same Babel + JSX stack the dev environment uses, so there's no separate production build.

A <base href="/"> tag in each generated page makes relative asset paths resolve from the root regardless of URL depth, so the same image references work at / and at /work/gridx-empower/.

Why not server-side rendering?
SSR requires a runtime. The goal was a site that deploys as a folder of files. The compromise — static HTML shells with client-side React hydration — gives crawlers what they need (title, description, OG tags) without a server dependency.
03 — Claude Code workflow

What I directed. What it generated.

Claude Code (Anthropic's CLI, running claude-sonnet-4-6) was the primary implementation tool for this site. The workflow was a tight loop: I wrote the spec, Claude Code wrote the code, I reviewed it in the browser, we iterated.

Being specific about this matters. "Built with Claude Code" covers a lot of ground — from "I described a button and accepted what it generated" to "I wrote a detailed spec and critically reviewed every line." This was closer to the latter.

What I directed
The full site spec: IA, typography system, color palette (OKLCH values chosen by me), section layout and hierarchy, component behavior, content strategy, accessibility requirements. Every major design decision — the editorial index aesthetic, the work hub structure, the confidential-work treatment using SVG schematics, the style-switcher panel — was specified before implementation. Metric accuracy: I corrected fabricated or misattributed numbers and supplied the verified data.
What Claude Code generated
CSS (following my system), HTML structure, React components (CaseStudy, Lightbox, WorkflowComparison, ConfidentialNotice, SVG Schematics), the build script, the axe accessibility audit loop, and the fix iterations when audits failed. It also caught several bugs I missed: a missing id="work" on the ledger section that broke nav anchor links, and an aria-controls wiring gap in the Q&A accordion.
Where it needed correction
Early drafts imported metrics from one case study into another (the 55-hour stat appeared in the wrong study). The tool can't verify facts — it surfaces what it finds and I have to catch what's wrong. The metric integrity pass was fully directed by me with verified source data. Claude Code never fabricated a quote or outcome; it flagged unknowns with [VERIFY] placeholders as instructed.

The session that built most of this site ran across multiple context windows over several days. Claude Code's memory system (project and user memory files) carried context between sessions so I didn't have to re-explain the design system on every restart.

04 — Design decisions

Three choices worth explaining.

Index-first layout — work is the page
Most portfolio sites lead with a hero that delays the work. This one leads with the work index. The hero is a compact strip. The reasoning: a recruiter opening this tab sees projects immediately, not a tagline. The "30-second tour" modal gives the elevator pitch to anyone who wants it without blocking everyone else.
Confidential work as a designed feature
Four of the eight case studies are fully confidential — no production UI can be shown. Rather than treating this as a gap, each confidential study uses an SVG "Schematics" component (abstracted system diagrams with annotation callouts), a WorkflowComparison component (before/after step counts and tool maps), and a ConfidentialNotice badge. The thinking is visible even when the screens aren't.
OKLCH for the color system
HSL's perceptual non-uniformity means that changing lightness in blue vs. yellow produces visually unequal results. OKLCH's lightness axis is perceptually linear, which makes it far easier to build a multi-theme system where all themes feel equally balanced. Every one of the six style-switcher themes was defined in OKLCH — changing the theme is a single :root swap of about 10 custom properties.

Lazy loading is applied to all work-index thumbnails below the fold. The LCP image (first work row, above fold) is not lazy-loaded. Explicit width/height on thumbnails prevents layout shift.

Babel Standalone and React UMD are the heaviest assets — they're the cost of JSX without a build step. For a portfolio with low traffic and no repeat-visit caching concerns, the tradeoff is acceptable. A production-grade version would pre-compile the JSX and ship a minified React bundle.

06 — Accessibility

WCAG 2.2 AA — verified.

Audited with axe-core 4.9.1 (injected via Puppeteer MCP) across the homepage and all eight case study pages. Starting state had two violation categories:

IssueBeforeFix
Color contrast (ink-3) 4.2:1 on 10px mono text (needs 4.5:1) Darkened --ink-3 from oklch(0.560) to oklch(0.480) in default and cream themes
Touch target size Doodle color swatches 16×16px (needs 24×24px per WCAG 2.2 §2.5.8) Increased .doodle-color to 24×24px
Results section labels 3.78–4.19:1 on dark ink background Increased paper opacity in color-mix() from 45% to 65%

Additional work done beyond the audit findings: global :focus-visible ring using var(--mark), skip-to-content link, prefers-reduced-motion media query disabling decorative animations, aria-controls / aria-labelledby wiring on Q&A accordion, role="dialog" + aria-modal + focus trapping on the image lightbox, and aria-live="polite" on the lightbox counter.

Final axe result: 0 violations, 23 passing rules on both homepage and case study pages.
